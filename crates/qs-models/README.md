# qs-models

The agent's model providers (P4-07, AGT-6, PRIN-9): each is a `qs_agent::Model` the agent loop
runs, and the person chooses which, with no account of ours and no telemetry.

- **Layer:** L6 agent. It depends on `qs-agent`, `serde`, `serde_json`, `tracing`, `ureq`
  (blocking HTTP over rustls with the webpki roots) and `keyring` (the OS keychain).
- **Spec sections:** none in `docs/spec/`; the wire formats are the providers' own, cited below.
- **Shipped:** yes.

## Providers

| `ProviderKind` | API | Default URL | Key |
| --- | --- | --- | --- |
| `Anthropic` | Messages API, `POST /v1/messages` | `https://api.anthropic.com` | `x-api-key` |
| `OpenAiCompatible` | Chat completions, `POST <base>/chat/completions` | `https://api.openai.com/v1` | `Authorization: Bearer` |
| `Ollama` | Ollama's OpenAI-compatible chat completions | `http://localhost:11434/v1` | none |

`ProviderModel::connect(config, &Keychain)` reads the key and talks HTTPS;
`ProviderModel::new(config, key, transport)` takes any `Transport`, which is how the tests
answer from scripts and a local stub server.

- **Anthropic:** tools as `name`, `description` and `input_schema`; a call is a `tool_use`
  block and its result a `tool_result` block in the next user message, results in a row in
  one message; `anthropic-version: 2026-10-21`; `output_config.effort` (`high` unless the
  configuration says otherwise); top-level `cache_control` so each turn reads the last one's
  prefix from the prompt cache; and on the models that take it, `fallbacks: "default"` with
  the `server-side-fallback-2026-07-01` beta, so a declined request is retried on a fallback
  model. A reply's content, thinking blocks included, is sent back unchanged on later turns.
  `stop_reason` `refusal` and `max_tokens` end the run with a message. The shapes are the
  Claude API reference's for raw HTTP (platform.claude.com, Messages API).
- **OpenAI-compatible:** quoted from `openai/openai-openapi`'s `openapi.yaml`, fetched
  2026-11-10: tools are `ChatCompletionTool` (`"type": "function"` and a `FunctionObject`);
  a call is `ChatCompletionMessageToolCall`, whose `function.arguments` is "as generated by
  the model in JSON format. Note that the model does not always generate valid JSON", so
  arguments that are not JSON reach the command as text, which refuses them with an error
  the model reads; a result is a `tool` message with its `tool_call_id`. `finish_reason`
  `content_filter` and `length` end the run.
- **Tool names:** `FunctionObject.name` "Must be a-z, A-Z, 0-9, or contain underscores and
  dashes, with a maximum length of 64", so a command id's `.` is sent as `_`
  (`edit.apply` as `edit_apply`) and mapped back from the tools offered.
- **Ollama:** docs.ollama.com, OpenAI compatibility: the local server is
  `http://localhost:11434/v1/`, and "The client requires an API key value, but Ollama
  ignores it", so none is sent. With Ollama nothing leaves the machine.

## Streaming

`Model::reply_streaming` asks for a stream (`"stream": true`) and calls back with each piece of
the reply's text as it arrives, for the agent panel. `Transport::post_stream` reads the answer
as server-sent events, each `data:` line in turn until `[DONE]`. The events are put back
together into the answer a non-streamed request gives, so one reader handles both:

- **Anthropic:** `content_block_start`, `content_block_delta` and `content_block_stop` for each
  block, then `message_delta` with the `stop_reason`, as the Claude API reference's streaming
  section shows. `text_delta` text is shown as it comes; `input_json_delta` fragments become
  the call's input; every other delta (`thinking_delta`, `signature_delta`) is appended field by
  field to its block, so a thinking block goes back whole. An `error` event fails the reply.
- **OpenAI-compatible:** `CreateChatCompletionStreamResponse` chunks; `choices[0].delta`'s
  `content` is the next text and its `tool_calls` are `ChatCompletionMessageToolCallChunk`s,
  joined by `index`.

## Keys

`Keychain` keeps each key under the service `quakec-studio` and the provider's
`ProviderConfig::key_name` (`anthropic`, `openai-compatible <url>`, `ollama <url>`): the
macOS Keychain, the Windows Credential Manager, or the Secret Service (over `zbus`, pure Rust)
on Linux. `MemoryKeys` keeps them for a session only.

A key is never written anywhere else:

- `ProviderConfig`, what a settings file keeps, has no key field.
- `Secret` has no `Display` or `Serialize`; its `Debug` is `Secret(<redacted>)`, so a log
  field, a panic message or a crash record shows no key. `Header::Secret` carries it to the
  request.
- Errors (`TransportError`, `KeyError`, `ProviderError`) hold the provider's or keychain's
  message, never a header.

## Tests

`src/tests.rs`: each provider's request and reply against scripted answers; Ollama over the
real HTTP client against a stub server on `127.0.0.1`, with no key sent; a run logged at
every level, a failed request and the settings form, none holding the key; keys per provider.
