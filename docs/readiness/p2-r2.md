# Readiness: P2 L2 syntax (P2-R2)

- **Issue:** #83 (`P2-R2`)
- **Reviewer:** an independent Claude agent session (the `reviewer` subagent); did not write
  the layer's code
- **Date:** 2026-10-21
- **Commit measured:** `6f12aefc20a28d2932519711d1c3fafaf8549838` (`main`, after #527), all
  four crates
- **Verdict:** Not ready

This is the fifth review of the layer. The fourth (commit `2a48d73`) was blocked on P2-80 to
P2-83 and on three ratchet failures; #488 restored the ratchets and #506 closed P2-80 to P2-84
and P2-87. Since then #516, #523, #524 and #527 ported FTEQCC's directive reader
(`crates/qc-preproc/src/fte_directive.rs`, P2-94 and P2-96 to P2-99), gave the syntax tree and
the project graph the same reading (P2-101, P2-102) and closed P2-105. Every issue the readiness
issue depends on is closed, and no issue labelled `L2-syntax` is open in the phase.

The Readiness run on `6f12aef` for the whole layer met every number it recorded: lines,
branches, spec citations and flakes are at or above their minimums for all four crates. But its
mutation job lost its runner twice at the same point in qc-preproc's mutants, so no crate's
mutation score was recorded, and a number not measured fails (section 2). The layer is not
ready on three issues filed here:

- **P2-109, the mutation measurement (`type:test`).** Both attempts of the mutation job ended
  with "The runner has received a shutdown signal" 31 to 32 minutes into qc-preproc's 1087
  mutants (`--no-shuffle`, so the same order each time), which the directive port of #516 to
  #527 nearly doubled from 556.

This review also ran 234 programs of its own through the builtin differential against the
pinned FTEQCC: 216 agree and 18 differ, in two classes.

- **P2-107, the file loader (`type:feature`).** FTEQCC's `QCC_LoadFile` decodes a file that
  starts with a UTF-16 or UTF-32 byte order mark, skips a UTF-8 one, and makes every NUL byte
  left a space. The profile reads a NUL as the end of the text, so text after it is never read, and
  its directive reader does not skip a UTF-8 byte order mark, so a directive on the first line
  after one is not run. 5 cases differ, and a UTF-16LE file FTEQCC compiles.
- **P2-108, `#if` values (`type:feature`).** `ParsePrecompilerIf` keeps each value in an `int`
  from C's `atoi`, which on an LP64 host is the low 32 bits of a saturating `strtol` and passes
  over only ASCII white space. The profile keeps an `i64` and passes over Unicode white space,
  so `#if 4294967296` is true where FTEQCC takes it as false, `#if 2147483648 < 0` false where
  FTEQCC takes it as true, and `#if` before U+00A0 and `1` true where FTEQCC takes it as false.
  13 cases differ.

The review added seven passing tests.

  - `reviewer_a_comment_opened_in_a_character_constant_hides_a_skipped_endif` (FTEF-14.37).
  - `reviewer_a_vertical_tab_after_a_skipped_hash_hides_the_endif` (FTEF-14.37).
