# Readiness: P2 L2 syntax (P2-R2)

- **Issue:** #83 (`P2-R2`)
- **Reviewer:** an independent Claude agent session (the `reviewer` subagent); did not write
  the layer's code
- **Date:** 2026-10-20
- **Commit measured:** `2a48d738d2740b051354495e950041526b466e3a` (`main`, after #486), all
  four crates
- **Verdict:** Not ready

This is the fourth review of the layer. The third (commit `5c552de`) met every ratchet and was
blocked on P2-69 (#471), FTEQCC builtin literals, which #473 closed. The P2-R3 reviews and the
self-reviews since added P2-71 to P2-73 and P2-75 to P2-79 to this layer, all closed by #479,
#483 and #486. #486 made FTEQW's compiler a porting upstream under ADR-0017's clean-port
policy and ported FTEQCC's macro expansion into `crates/qc-preproc/src/fte_macro.rs`, with a
new bound and diagnostic, `E0120` (FTEF-14.19, QCD-8.12).

The Readiness run on `2a48d73` for the whole layer fails three of its ratchet checks, all
from code added since the last passing measurement. The layer is not ready, on those
failures and on four defects this review found, three by comparing the port with the pinned
FTEQCC and one by measuring the new bound:

- **The ratchets.** qc-lexer lines are 99.7% against a minimum of 100, qc-preproc branches
  90.5% against 91, and two qc-preproc mutants survive unlisted (section 2). The orchestrator
  is closing this gap in a separate PR with its own plan entry, so this review files no issue
  for it; qc-lexer and qc-preproc are to be measured again once it merges.

- **P2-80, macro arguments (`type:feature`).** FTEQCC's argument scanner skips only `"`
  strings, so a `,` or `)` in a character constant or a comment ends an argument, and a string
  ending in `\` does not end; and a built-in constant an argument copies as its value replaces
  the white space before it. 13 cases differ from the pinned FTEQCC.
- **P2-81, stored macro bodies (`type:feature`).** FTEQCC drops a body's comments and line
  continuations, so a function-like macro's name and `(` written apart only by them in a body
  take their arguments; its `#define` reader ends a body at a `//` after an escaped `\"`; and a
  duplicate parameter name is an error. 6 cases differ.
- **P2-82, variadic macros (`type:feature`).** FTEQCC's `__VA_COUNT__` and the comma `##`
  removes before an empty `__VA_ARGS__`, and empty variadic arguments. 4 cases differ.
- **P2-83, the expansion bound (`type:feature`).** One expansion writes as many tokens as its
  body names its parameter times the argument's length, past FTEF-14.19's stated 2^22 tokens
  with no `E0120`: a 32018-byte file writes 64000000 tokens under either dialect, and the test
  process that preprocessed it under both peaked at 10.4 GB.

Each FTEQCC difference is in the class the builtins differential's macro family covers
(initialisers and statements a macro writes, compared with the pinned FTEQCC); the family's
cross product did not contain them. The review added six passing tests.

## 5. Independent review (TEST-9)

- **Reviewer and time spent:** an independent Claude agent session, about three hours across
  this review and the L3 one. It read `fte_macro.rs` and #486's changes to `lib.rs` against
  FTEQCC's `QCC_PR_PreProcessor_Define`, `QCC_PR_ExpandPreProcessorMacro`,
  `QCC_PR_CheckCompConst` and `QCC_COM_Parse2` at the pinned commit (fetched by `cargo xtask
  oracles`); built the oracles on macOS arm64; ran 131 cases of its own through the builtins
  differential (section 3); and measured the expansion bound in release builds.
- **The port against ADR-0017 and the porting checklist.** It meets them. The header keeps
  FTE's copyright line above ours and has one `Ported from fte-team/fteqw@f937b9d...` line per
  file (`qcc_pr_lex.c` and `qcc_cmdlib.c`), which `cargo xtask licenses` checks; each function's
  rustdoc names the FTEQCC function it follows and `fte_substitute` says `Implements
  FTEF-14.14 to FTEF-14.16, FTEF-14.20 and QC-9.16`; the behaviour is in FTEF-14.13 to
  FTEF-14.20, with citing tests; the differential is the proof. The code is written in the
  preprocessor's token model (a `Writer` over `PpToken`s, state on `Run`, no globals), not
  FTEQCC's buffer and pointer, and the C appears only as quoted citations. One naming note: the
  module's `enum Copy` shadows the prelude's `Copy` in `fte_macro.rs`; it compiles and is not a
  defect.
- **The bound, E0120 (FTEF-14.19).** Checked before each expansion and counted after it, so it
  holds over many small expansions (the shipped tests) but not within one. A function-like
  macro whose body names its parameter `n` times, given an argument of `m` tokens, writes
  `n * m` tokens in one expansion. Release build, macOS arm64, `#define D(x)` and `n` times
  `x`, then `D(` with `m` times `1` and `)`:

  | n = m | File | Tokens | E0120 | Time (FTEQCC; vanilla) | Peak memory |
  | --- | --- | --- | --- | --- | --- |
  | 2000 | 8018 bytes | 4000000 | no | 0.21 s; 0.27 s | |
  | 4000 | 16018 bytes | 16000000 | no | 0.91 s; 1.16 s | |
  | 8000 | 32018 bytes | 64000000 | no | 5.5 s; 7.5 s | 10.4 GB (one process ran this row and the 2000 row, both dialects) |

  FTEF-14.19 says the profile writes "at most `FTE_MAX_EXPANDED_TOKENS` = 2^22 tokens"; the
  vanilla dialect states no bound. Nested calls (`D(D(...D(1)...))` with `#define D(x) x x`) do
  not grow: the inner calls are in `D`'s own chunk or hide set, as FTEF-14.17 and QC-9.4 say.
- **The port against the pinned FTEQCC.** Of the review's 131 cases, the 27 on conditional
  directives, `#undef`, `#append`, comments and continuations in object-like bodies agree.
  Pastes (`n##n`, `Q##x`, pastes inside another macro's arguments, `# #` and `#/**/#`),
  stringified built-in constants and strings with commas, own-name arguments, empty and extra
  arguments, nested calls and calls after an expansion ends agree too. The differences, each
  "oracle" against "profile" (`void() f = USE;` after the definitions):

  | Definitions | Use | FTEQCC | Profile | Issue |
  | --- | --- | --- | --- | --- |
  | `#define E(n) :n` | `E(',')`, `E(')')`, `E('(')` | refused ("Bad vector") | builtins 44, 41, 40 | P2-80 |
  | `#define M(x) x` | `M(#5 /* ) */)`, `M(#5 /* , */)`, `M(#5 // )` and a line break and `)` | refused ("EOF inside comment") | builtin 5 | P2-80 |
  | `#define E(n) n` | `E(:"ex\\")`, `E(:"ex\\") ")"`, `E(#5:ex_a\` and a line break and `)` | refused | bound | P2-80 |
  | `#define S(a) #a` | `:S(e'x)` | bound by `e'x` | refused | P2-80 |
  | `#define E(n) n`, `#define K(x) x` | `E(# __LINE__)`; `E(#//` and a line break and `__LINE__)`; `K(#` and a line break and `__LINE__)` | builtin 2; 3; 3 | refused | P2-80 |
  | `#define M(x) x` and `#define K M /**/ (#5)`, `M/**/ (#5)`, `M \` and a line break and `(#5)`, `M\` and a line break and ` (#5)` | `K` | builtin 5 | refused | P2-81 |
  | `#define N :"ex\"_a//"` | `N` | refused | bound by `ex"_a//` | P2-81 |
  | `#define E(n, n) n` | `E(#5, 6)` | refused ("duplicate macro paramter name") | builtin 5 | P2-81 |
  | `#define V(...) :__VA_COUNT__` | `V(a, b)` | builtin 1 | bound by `__VA_COUNT__` | P2-82 |
  | `#define V(a, ...) #5:__VA_COUNT__` | `V(a, b)` | refused | bound by `__VA_COUNT__` | P2-82 |
  | `#define V(a, ...) a,##__VA_ARGS__` | `V(#5)` | builtin 5 | refused | P2-82 |
  | `#define E(...) #5 __VA_ARGS__` | `E(, )` | builtin 5 | refused | P2-82 |
