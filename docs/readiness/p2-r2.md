# Readiness: P2 L2 syntax (P2-R2)

- **Issue:** #83 (`P2-R2`)
- **Reviewer:** an independent Claude agent session (the `reviewer` subagent); did not write
  the layer's code
- **Date:** 2026-10-20
- **Commit measured:** `5c552de592b4cbd08e17a563e7d23834acf84289` (`main`, after #467) for
  qc-preproc and qc-syntax; `a82c1c05ec5131e517c0343d012881ff7eac1d54` (after #458) for
  qc-lexer and `368abee8a31940dbdf6b01a32bf9b4a15a4601aa` (after #446) for qc-project, neither
  of which has changed since
- **Verdict:** Not ready

This is the third review of the layer. The second met every ratchet and was blocked on two
defects, both closed by #467:

- **P2-65 (#464), preprocessor stack overflow: fixed.** A hide-set node now unlinks its chain
  in a loop when dropped, and a live count per macro name answers "not hidden" at once for a
  name no live node holds (QC-9.13). The shipped test preprocesses chains of 10000 and 100000
  under both dialects on a 2 MiB thread; this review ran it in a debug and a release build, and
  the `qs-tests` case that puts the 100001-line file through `Db::analyze_module` likewise.
  All four passed.
- **P2-66 (#465), FTEQCC builtin initialisers: fixed.** `= #"name"`, `= :name`, `= :"name"`,
  `= :N`, `= :N:name` and `:name` after a function declarator parse under the FTEQCC profile,
  and `Builtin::engine_name` gives the name (FTE-17.5).

The Readiness run on `5c552de` for qc-preproc and qc-syntax passes all 14 checks. The layer is
still not ready, on one defect this review found by comparing builtin initialisers with the
pinned FTEQCC:

- **P2-69, FTEQCC builtin literals (`type:feature`).** Three forms read differently from
  FTEQCC. A `d` literal is a double, which FTEQCC's `QCC_PR_ParseInitializerType_Internal` does
  not take: FTEQCC reports "Bad builtin immediate" for `= #16d;`, `= #16.0d;` and `= :16d;`.
  The profile accepts all three, and `builtin_binum` gives 16. FTEQCC's `QCC_PR_Lex` reads `#`
  as a builtin only when the next byte is `"`, `-`, a digit, `)` or `,`, so it reports
  "Explicit precompiler usage when not defined" for `= # 5;`, `= # "nm10";` and `= #'a';`,
  which the profile accepts. And FTEQCC joins adjacent strings: it binds `= #"ab" "cd";` by
  the name `abcd`, where the profile reports E0203.

The issue is filed in section 5; the review added six passing tests.

## 5. Independent review (TEST-9)

- **Reviewer and time spent:** an independent Claude agent session, about two hours on this
  re-review. It read #467's changes to qc-preproc and qc-syntax; put five long macro forms
  through the preprocessor under both dialects in debug and release builds; and compared 56
  builtin initialisers with the pinned FTEQCC and three with id's `qcc` (`cargo xtask oracles
  build`, macOS arm64, reading each builtin's `first_statement` from the `progs.dat` written),
  against the FTEQCC profile's diagnostics, `builtin_binum` and `Builtin::engine_name`.
- **P2-65, re-checked:** besides the shipped chain test, a chain of 100000 function-like macros
  (`#define F1(x) F0(x)`, ...) expands to `1`, and `F(F(...F(1)...))` nested 100000 deep
  expands its outer call and leaves the inner ones, all on a 2 MiB thread under both dialects
  in debug and release builds. A chain whose every macro also names the chain's head
  (`#define M1 M0 M9999`, ...) expands correctly, but in quadratic time: the head has live
  hide-set nodes, so each use of it walks its hide set. At 100000 macros it takes 4.5 s in a
  release build, against 0.1 s for the plain chain (section 7).
- **P2-66, re-checked against FTEQCC and found to agree:** `void bx() :ex_c;`,
  `void bx() = :ex_d;`, `void(float a) bx :ex_e, by :ex_f;`, `var void() bx :ex_g;`,
  `void() bx : ex_h;`, a local `= :nm4`, `bx :5;` and `bx :5:nm;` compile and parse with the
  same names and numbers; `.void() fth :nm6;`, `void(void() cb :nm7)`, `= :nm8:;`,
  `= :5:"nm";` and `= #0:"nm9";` are errors in both. `:'a'` is 97 and `:'\n'` 10 in both;
  `#1e3`, `#16iu`, `#08` and `#1.5i` are errors in both. `#16f`, `#5.0f`, `#1.`, `#0x10`,
  `#010` (8), `#-0`, `#16777217i` and `#0x10i` bind the same numbers.
- **Tests added** (six, all passing):
  - `crates/qc-preproc/src/tests/reviewer.rs`:
    - `reviewer_a_chain_of_function_macros_expands_to_its_end` (QC-9.13): 100000 function-like
      macros, both dialects, a 2 MiB thread.
    - `reviewer_a_call_nested_in_its_own_argument_expands_once` (QC-9.13): a call nested
      100000 deep in its own argument.
    - `reviewer_a_chain_that_names_its_head_leaves_the_head_unexpanded` (QC-9.13): a
      10000-long chain whose macros also name its head, where the live count is above 0 and
      the hide set must still be read.
  - `crates/qc-syntax/src/tests/reviewer.rs`:
    - `reviewer_fteqcc_colon_builtins_follow_any_function_declarator` (FTE-17.5): the six `:`
      forms above, with the names FTEQCC binds.
    - `reviewer_fteqcc_colon_is_no_builtin_on_a_field_or_parameter` (FTE-17.5): the field and
      parameter forms FTEQCC rejects.
    - `reviewer_fteqcc_colon_numbers_bind_as_hash_numbers` (FTE-17.6): `:'a'`, `:'\n'`,
      `:123456789`, `#0x10i` and `bx :5` bind 97, 10, 123456792, 16 and 5.
- **Defects found** (each blocks readiness; issue in `plan/backlog/p2.yaml`, synced to GitHub
  after this PR merges):
  - **P2-69, FTEQCC builtin literals (`type:feature`):** above. The pinned FTEQCC's results:

    | Input | FTEQCC | FTEQCC profile |
    | --- | --- | --- |
    | `= #16d;`, `= #16.0d;`, `= :16d;` | Bad builtin immediate | no error, `builtin_binum` 16 |
    | `= # 5;`, `= # "nm10";`, `= #'a';` | Explicit precompiler usage when not defined | no error, binding 5, `nm10` and 97 |
    | `= #"ab" "cd";`, `= :"x" "y";` | bound by `abcd` and `xy`, 0 warnings | E0203; `engine_name` gives `ab` and `x` |

    id's `qcc` binds the vanilla `= # 5;` as 5, which the vanilla profile also accepts.
    Keying `#16d` and `#"ab" "cd"` as FTEQCC binds them is in P2-70's L3 half
    (`docs/readiness/p2-r3.md`).
