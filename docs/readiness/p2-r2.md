# Readiness: P2 L2 syntax (P2-R2)

- **Issue:** #83 (`P2-R2`)
- **Reviewer:** an independent Claude agent session (the `reviewer` subagent); did not write
  the layer's code
- **Date:** 2026-10-19
- **Commit measured:** `58c060c12c4ba72f0874dd738fab09a00fe700e6` (`main`; the head the
  Readiness run resolved)
- **Verdict:** Not ready

The L2 syntax layer passed P1-R2 and has grown the FTEQCC profile since (P2-26, P2-38 to
P2-42). It does not pass the bar again:

- **A behavioural defect (QC-27.15):** under the FTEQCC profile the parser does not bound the
  depth of its tree. 100000 repeats of a prefix `-`, `+`, `++` or `--`, of `()` or `*` after a
  type, or of a leading `-` in a state frame or a parameter default overflow the stack and
  abort the process; at 2000 repeats the two type forms report no error at all. QC-27.15 says "this compiler
  bounds the depth of its syntax tree so that no input can exhaust its stack".
- **TEST-10 (ratchets):** three crates have fallen below the minimums P1-R2 committed to
  `ratchets.toml`: qc-lexer lines and branches, qc-syntax lines and branches, and qc-project
  branches. Every crate still clears the 90% and 80% bars.
- **TEST-2 (mutation):** three crates have surviving mutants that are neither killed nor
  listed as equivalent, and are below their P1-R2 minimums: qc-lexer 90.5% (22 survivors,
  minimum 100), qc-preproc 93.1% (27 beyond the two recorded equivalents, minimum 98) and
  qc-syntax 90.2% (99 survivors, minimum 100). The Readiness `ratchet` job fails on eight
  problems in all.
- **TEST-4, TEST-5:** the FTEQCC profile is neither fuzzed nor property-tested: the `parser`
  fuzz target and the lossless, determinism and token-deletion properties call only the vanilla
  `parse`, and the deletion check runs only on id 1.01.

Each is filed as a blocking issue (section 5); the review added six passing tests.

## 5. Independent review (TEST-9)

- **Reviewer and time spent:** an independent Claude agent session, about two hours across
  both P2 reviews. It generated deep and long inputs for 37 constructs under both profiles and
  measured each parse's tree depth and diagnostics, then fed the same inputs to the semantic
  model above.
- **Tests added** (six, all passing):
  - `crates/qc-syntax/src/tests/reviewer.rs`:
    - `reviewer_fteqcc_keeps_the_vanilla_parenthesis_limit` (QC-27.15): parentheses nest
      exactly as deep under the FTEQCC profile as under vanilla.
    - `reviewer_fteqcc_operator_chains_stop_at_the_limit` (QC-27.15): 20000 repeats of `?:`,
      `?:` with no middle, `->`, `[]`, the comma operator, a cast, `sizeof` and `!` report
      E0509, keep the tree within 4 x `QC_MAX_NESTING` and give back every byte.
    - `reviewer_fteqcc_statement_nesting_is_bounded` (QC-27.15): `do`, `for` and `if` nested
      20000 deep.
    - `reviewer_fteqcc_soup_round_trips` (QCD-1.4): FTEQCC punctuation soup round-trips with
      every diagnostic inside the input.
    - `reviewer_fteqcc_parse_is_deterministic` (QCD-1.4).
  - `crates/qc-preproc/src/tests/fteqcc.rs`: `reviewer_long_logical_chains` (FTEF-14.11):
    30-long `||` and `&&` chains take the right side, and 100000-long chains of `||`, `!` and
    `(` take one side without exhausting the stack.
- **Defects found** (each blocks readiness; issues in `plan/backlog/p2.yaml`, synced to GitHub
  after this PR merges):
  - **P2-50, unbounded nesting under the FTEQCC profile (`type:feature`).** At 100000 repeats
    `parse_with(.., Dialect::Fteqcc)` aborts with a stack overflow on `a = ---...a;`,
    `a = +++...a;`, `++++...a;`, `----...a;`, `float()()()... f;`, `float***... p;`,
    `void() f = [---...1, f] {};` and `void(float a = ---...1) f;`. At 2000 repeats the tree
    is 2003 nodes deep for the two type forms with no diagnostic, 969 for prefix `-` and `+`
    and 1948 for prefix `++` and `--` (E0509 reported, nesting carried on), 773 for nested
    `struct {` and 774 for C-style parameter lists; the vanilla forms stop near 3 x
    `QC_MAX_NESTING` (771 for nested parameter lists). The same trees overflow the semantic
    model's stack at 3000 repeats. The issue also asks for the `#if` reader's nesting limit
    (`MAX_DEPTH = 64` in `qc-preproc/src/cond.rs`) to be a spec statement: FTEF-14.11 says only
    that the errors FTEQCC reports make an expression false, yet `fteqcc_errors_are_false`
    cites it for 100 nested parentheses.
  - **P2-51, FTEQCC fuzzing and properties (`type:test`):** section 3.
  - **P2-52, the P1-R2 ratchets (`type:test`):** the coverage and mutation numbers below their
    minimums in section 2, restored by tests rather than by lowering the minimums.
