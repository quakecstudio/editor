# Readiness: P2 L3 semantics (P2-R3)

- **Issue:** #84 (`P2-R3`)
- **Reviewer:** an independent Claude agent session (the `reviewer` subagent); did not write
  the layer's code
- **Date:** 2026-10-20
- **Commit measured:** `bdfebf59cc01adfa1db2dc5cdbc60c775f3afe12` (`main`, after #473)
- **Verdict:** Not ready

This is the fourth review of the layer. The third (commit `5c552de`, run
[39381064911](https://github.com/quakecstudio/editor/actions/runs/39381064911)) met every
ratchet and was blocked on one defect, P2-70 (#472), builtin redeclarations. #473 has closed
it: under FTEQCC a builtin initialiser is now its `binum` and engine name, with the
definition's own name standing in for none, and a second one is the same value only when
FTEQCC would reuse the definition's own builtin function (FTE-23.7, FTEF-17.10). #473 also
added `cargo xtask oracles builtins`, a differential of 8068 builtin initialiser cases against
the pinned FTEQCC and id's `qcc`. The Readiness run on `bdfebf5` passes every check
`cargo xtask ratchet` makes.

The layer is not ready, on one defect this review found:

- **P2-74, macro expansions rendered with a space between every token (`type:feature`).**
  The semantic model renders a module's expansion as text and parses that
  (`crates/qc-sema/src/expand.rs`, `render` and `adjacent`); two tokens a macro made are never
  rendered touching. Since #473 made the FTEQCC `#` a builtin only when the next byte is `"`,
  `-`, a digit, `)` or `,` (FTE-23.1), a builtin from an object-like macro reaches the parser
  as `# 5` and is `E0209`: `#define B #5` then `void() f = B;`, and the same with `#-5`,
  `#"ex_a"` and `#5:ex_a`. The pinned FTEQCC compiles each with no error and binds `#5` as
  builtin 5 named `f` and `#5:ex_a` as builtin 5 named `ex_a`; before #473 the profile accepted
  them. The same rendering breaks a C label made by a macro (FTEF-18.23): `#define L lbl:`
  then `void() f = { L goto lbl; };` gives `W0313`, `E0204` and `E0301`, where FTEQCC compiles
  it. The issue also covers a gap in qc-sema's README: its **Spec statements** line does not
  list FTE-23.7, which `LiteralValue::builtin_function` and `Resolver::same_value` implement,
  so the Readiness `spec` job does not count that statement against the crate (its tests do
  cite it, so the workspace ratchet holds it).

Everything else meets the bar; the review added seven passing tests.

## 5. Independent review (TEST-9)

- **Reviewer and time spent:** an independent Claude agent session, about two hours on this
  re-review. It read #473's changes to qc-sema and qc-engines, built the oracles (`cargo xtask
  oracles build`, macOS arm64), and compared about 70 builtin programs outside the
  differential's cross product with the pinned FTEQCC (`-Tid`, and `-Fautoproto` for the
  autoprototyping cases), reading each function's `first_statement` and name from the
  `progs.dat` it wrote, against `Db::analyze_module` under the FTEQCC profile.
- **P2-70, re-checked:** fixed. `#0:ex_a` then `#0:ex_b`, `#5:ex_a` then `#5:ex_b` and `#5`
  then `#5:ex_a` are `E0206`; `:ex_a` then `:"ex_a"`, `#0:ex_a` then `:ex_a` and `#"ex_a"`
  then `:ex_a` are accepted; FTEQCC agrees on each. The differential's 0 unexplained cases on
  three OSes (section 3) cover the rest of #472's acceptance; `#16d` gives no `W0311` and
  `#"ab" "cd"` is keyed `abcd` (`qc-engines` tests `double_literals_give_no_key` and
  `joined_strings_key_a_builtin_by_their_name`).
- **Behaviour checked against FTEQCC and found to agree:** the function FTEQCC reuses is the
  first made with a number and name across files, and left to right within one declaration
  (`void() f = #5:ex_a, g = #5:ex_a;` then `g` again is `E0206`, then `f` again is not); a
  macro that gives the number or engine name (`:N`, `#5:EN`, `:EN`) compares as its expansion;
  a `noref` builtin is never compared; `var` and `const` change nothing; with `-Fautoproto`
  the outcomes are those of one reading; a builtin after a body is `W0206` and a body after a
  builtin `E0206`; a different function type is `E0205`; `::ex_a`, `:#5`, `#'a'` and
  `#5:ex_a:ex_b` are errors in both.
- **Tests added** (seven, all passing):
  - `crates/qc-sema/src/tests/reviewer.rs`:
    - `reviewer_the_reused_builtin_function_is_found_across_files` (FTE-23.7)
    - `reviewer_builtins_compare_after_macro_expansion` (FTE-23.7)
    - `reviewer_a_noref_builtin_is_never_compared` (FTEF-17.8)
    - `reviewer_autoprototyping_compares_builtins_as_one_reading` (FTE-22.3)
    - `reviewer_one_declaration_makes_its_functions_in_order` (FTE-23.7)
  - `crates/qc-engines/src/tests.rs`:
    - `reviewer_fteqcc_keys_a_character_and_a_spaced_name_by_number` (ENGT-4.13): `:'a'` is
      keyed 97 and `#9000 : ex_a` 9000, as FTEQCC binds them.
    - `reviewer_the_first_file_keys_a_builtin_given_in_two` (ENGT-4.12)

  Removing the first-function check from `Resolver::same_value` (keeping only `first == key`)
  fails three of the qc-sema tests; restored before commit.
- **Defects found** (each blocks readiness; issue in `plan/backlog/p2.yaml`, synced to GitHub
  after this PR merges):
  - **P2-74, macro expansions rendered with a space between every token (`type:feature`):**
    above. The test for its acceptance cannot be committed passing until the fix lands.
