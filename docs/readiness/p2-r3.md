# Readiness: P2 L3 semantics (P2-R3)

- **Issue:** #84 (`P2-R3`)
- **Reviewer:** an independent Claude agent session (the `reviewer` subagent); did not write
  the layer's code
- **Date:** 2026-10-20
- **Commit measured:** `5c552de592b4cbd08e17a563e7d23834acf84289` (`main`, after #467)
- **Verdict:** Not ready

This is the third review of the layer. The second (commit `368abee`, run
[39338765602](https://github.com/quakecstudio/editor/actions/runs/39338765602)) met every
ratchet and was blocked on one defect, P2-67 (#466), builtin keys. #467 has closed it: a
builtin is keyed by the `int` the dialect's compiler binds (`qc_syntax::builtin_binum`), so
`#123456789` is 123456792 under both dialects, and FTEQCC's `#"NAME"`, `:"NAME"` and `:NAME`
are keyed by name (ENGT-4.12 to ENGT-4.14). #467 also changed how qc-sema compares a builtin
initialised twice (`LiteralValue::of_fteqcc` in `src/lower.rs`). The Readiness run on `5c552de`
passes every check `cargo xtask ratchet` makes.

The layer is not ready, on one defect this review found in that change:

- **P2-70, builtin redeclarations (`type:feature`).** Under FTEQCC, qc-sema now compares a
  builtin with a number as `#<binum>` alone and drops its engine name, so `void() f = #0:ex_a;`
  then `void() f = #0:ex_b;`, `#5:ex_a` then `#5:ex_b`, and `#5` then `#5:ex_a` give no
  E0206. The pinned FTEQCC reports "incompatible redeclaration" for each. A builtin with no
  number is still compared by its text, so `:ex_a` then `:"ex_a"`, `#0:ex_a` then `:ex_a`, and
  `#"ex_a"` then `:ex_a` are E0206. FTEQCC compiles each of those with 0 warnings. FTEQCC
  reuses a builtin function only when its `binum` and its engine name match (the definition's
  own name stands in when it has no engine name), in `QCC_PR_ParseInitializerType_Internal`.
  The issue also covers the L3 half of P2-69 (`docs/readiness/p2-r2.md`): a `d` literal such
  as `#16d` is keyed 16, though FTEQCC rejects it as "Bad builtin immediate".

Everything else meets the bar; the review added three passing tests.

## 5. Independent review (TEST-9)

- **Reviewer and time spent:** an independent Claude agent session, about two hours on this
  re-review. It read #467's changes to qc-sema and qc-engines and compared builtin keys and
  builtin redeclarations with id's `qcc` and the pinned FTEQCC (`cargo xtask oracles build`,
  macOS arm64), reading each builtin's `first_statement` from the `progs.dat` they wrote: 14
  redeclaration pairs through `Db::module_index` against FTEQCC, and the number forms of
  section 5 of `docs/readiness/p2-r2.md` through `builtin_number`.
- **P2-67, re-checked:** fixed. id's `qcc` binds `void() bx = #123456789;` as 123456792 and
  `#16777217` as 16777216, and qc-engines names 123456792 in its `W0311` under the vanilla
  dialect; FTEQCC binds `#123456789` and `:123456789` as 123456792, and qc-engines keys both
  so. `#"ex_bprint"`, `:"ex_bprint"`, `:ex_bprint` and `bprint :ex_bprint;` are keyed by name.
  The deep-chain case found from here last time (P2-65), a 100001-line file of chained
  `#define`s through `Db::analyze_module`, passes on a 2 MiB thread in debug and release builds
  (`cargo test -p qs-tests a_long_chain_of_macros`, with and without `--release`).
- **Behaviour checked against FTEQCC and found to agree:** `#16` then `#16.0`, `#0:ex_a` twice,
  `#5:f` after `#5` for a definition `f`, and `#0:ex_a` then `#00:ex_a` are accepted; `#5` then
  `#6`, `#16777217i` then `#16777216`, and `#0:ex_a` then `#5:ex_a` are E0206.
- **Tests added** (three, all passing):
  - `crates/qc-engines/src/tests.rs`:
    - `reviewer_vanilla_names_the_number_qcc_binds` (ENGT-4.12): a vanilla `#123456789` is
      `W0311` naming builtin 123456792, as id's `qcc` binds it.
    - `reviewer_fteqcc_keys_a_colon_number_as_a_hash_number` (ENGT-4.13): `:123456789` is keyed
      123456792, as the pinned FTEQCC binds it.
  - `crates/qc-sema/src/tests/reviewer.rs`:
    `reviewer_builtins_initialised_again_compare_by_number` (FTEF-17.5): `#16` then `#16.0`
    and `#0:ex_a` twice are accepted, `#5` then `#6` is E0206, each as FTEQCC compiles it.
- **Defects found** (each blocks readiness; issue in `plan/backlog/p2.yaml`, synced to GitHub
  after this PR merges):
  - **P2-70, builtin redeclarations (`type:feature`):** above.
  - Found from here against the layer below and filed there (`docs/readiness/p2-r2.md`): the
    FTEQCC profile accepts the builtin forms `#16d`, `# 5`, `# "x"` and `#'a'`, which FTEQCC
    rejects, and rejects `#"ab" "cd"`, which FTEQCC binds as `abcd` (P2-69).
